# Checking a CI certificate

Details behind the [CI signer section of the README](README.md#ci-signer-githubworkflowsci-signeryml).

## The judge hash
Whoever can push to `main` can change the judge and get a CI certificate for a failing agent, so a CI certificate carries a judge hash in `run_ref`: the runner and its package files, suites, agents, attacks, scenarios, `deploy/`, `demo/txs.json` (the contract code hash CI accepts) and every workflow, without tests and authorship records. `make judge-hash REF=<commit>` prints it for any commit; judge code at the time of writing: `11869f04fc25ef8ca51c0693ee027bee567c2374` (commit `fb1aa7f`). The hash is written by the committed code itself, so a different hash shows the judge changed, and an equal one proves nothing on its own. To check a CI certificate: take the run id from `run_ref`, read that run's `head_sha` from the GitHub API, run `make judge-hash REF=<head_sha>`, rebuild the report from that run's artifact and compare it with the certificate's `report_hash`; then review `git diff` on those paths since a commit you trust. This only means something while `main` is protected against force-push and deletion, which it is since Oct 29, 2026.

## Cherry-picking stays visible
Every run is in the Actions tab, titled with agent and mode. Before certifying, the sign step prints every earlier run except smoke runs on `main` next to the new certificate, and refuses to certify if it cannot read the run history. A failed full run whose artifact is intact revokes the CI account's earlier certificate on chain, if there is one; a failed run with nothing to revoke, a run deleted by a repo admin, or one cancelled before signing leaves no on-chain trace. An owner who wants only CI-backed certificates trusts `lt-dopusk-ci-signer.testnet` as a signer.
